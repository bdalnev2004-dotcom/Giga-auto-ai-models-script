# Giga Automation — контекст проекта (хендофф для Claude Code)

Этот файл — сводка всего, что обсуждалось и было решено в чате с Claude до передачи
проекта в Claude Code. Клади его в корень репозитория (например `PROJECT_CONTEXT.md`)
и скажи Claude Code его прочитать перед началом работы.

---

## 1. Что это

**Giga Automation** — система автоматизации SMM-фермы: управление ~20 аккаунтами
в Instagram (AI-инфлюенсеры + бренд-аккаунты) через Telegram-бота, с AI-генерацией
контента и утверждением одной цифрой в чате.

Источник концепции — мастер-документ Бориса (в 5 разделах: концепция дашборда,
регламент бота, workflow для brand/blogger-аккаунтов, плейбук контента для каруселей,
HTML-шаблон каруселей). В процессе работы часть концепции была уточнена и сужена —
см. раздел 3 ниже.

## 2. Архитектура

Один бэкенд («мозг») + Telegram-бот как интерфейс (дашборд заменён на CRM — см. п.5).

**Карточка аккаунта** = матрица платформ (какие включены + креды в зашифрованном
волте). **Единая нумерация файлов** в Google Drive синхронизирована с номерами,
которые пользователь называет в чате при аппруве.

Поток данных (детальная схема была визуализирована ранее в чате):
```
Триггер (текст в Telegram)
  → определение сценария (triggers.py)
  → контекст аккаунта (/account N, карточка из БД)
  → уточняющие вопросы (Claude, только недостающие)
  → генерация (Claude / Higgsfield / ElevenLabs / Vyra)
  → сохранение в Google Drive (нумерованные варианты)
  → аппрув (номер / ✅ / ❌ / список номеров)
      ❌ → назад на генерацию с revision_notes (цикл)
      ✅ → запись в БД + маршрутизация на публикацию
  → публикация (см. п.3 — сейчас только HikerAPI/Reels)
  → журнал (audit_log)
```

Параллельно — крон-джобы (12:00/15:00 напоминания, 20:00 публикация), которые
запускают тот же STAGE_01, но не человеком, а планировщиком.

## 3. КЛЮЧЕВОЕ УТОЧНЕНИЕ ОБЪЁМА (важно не потерять)

**Автоматический постинг — только Instagram Reels через instagrapi.**

> **Уточнено при реализации (август 2026):** изначально предполагался постинг
> через HikerAPI. Это оказалось невозможно — **HikerAPI работает только на
> чтение** публичных данных Instagram (профили, посты, сторис, рилсы,
> комментарии, хэштеги); эндпоинтов upload/publish/post у него нет вообще.
> Публикация реализована через **instagrapi напрямую** (приватный API,
> запускается у себя): `clip_upload` (рилс), `photo_upload` (фото),
> `video_upload_to_story`/`photo_upload_to_story` с `StoryLink` (сторис со
> ссылкой — ровно то, ради чего HikerAPI и выбирали).
> `services/hikerapi_service.py` удалён, вместо него — `services/instagram_service.py`.
> `HIKERAPI_ACCESS_KEY` в конфиге оставлен: HikerAPI по-прежнему полезен для
> чтения (аналитика, сбор референсов), но это отдельная задача.

- TikTok (Blotato), YouTube, VK — **вне текущего объёма**. Blotato-адаптер оставлен
  в коде как заглушка на будущее, но никуда не подключён и не должен вызываться.
- Фото/карусели/сторис можно генерировать и утверждать как контент (остаются
  в Drive), но автопостинг для них не реализуется.
- При создании аккаунта в БД сеется только одна строка `AccountPlatform` —
  `Platform.instagram`. TikTok/YouTube/VK остаются в enum `Platform` на будущее,
  но не создаются активными.
- Таблица маршрутизации публикации (`handlers/approvals.py::PUBLISH_ROUTING`)
  содержит только `"reels_edit": "instagram"` (+ `"tg_post": "telegram_channel"`,
  это отдельная история — публикация в собственный TG-канал персонажа, не
  соцсеть).

**Критический путь для первого рабочего цикла теперь короче, чем казалось
изначально**: нужны только `services/instagram_service.py` (публикация рилса) и
`services/vyra_service.py` (сборка рилса из сырых материалов). Higgsfield,
ElevenLabs, Blotato — не блокируют MVP, можно отложить.

## 4. Технологический стек

- **Бот**: Python, `aiogram` v3, FSM-диалоги (`aiogram.fsm`)
- **БД**: PostgreSQL, `SQLAlchemy 2.0` (async), `asyncpg`
- **FSM-хранилище**: Redis в проде (`aiogram.fsm.storage.redis`), MemoryStorage —
  только для локальной разработки (падает при рестарте процесса)
- **Оркестрация/копирайт**: Claude API (`anthropic` python SDK)
- **Хранилище файлов**: Google Drive (Service Account, `google-api-python-client`)
- **Волт кредов**: `cryptography.Fernet` (симметричное шифрование), ключ —
  отдельно от кода/репозитория
- **Планировщик**: `APScheduler`, таймзона `Europe/Moscow`
- **Инфраструктура**: Docker + Docker Compose (bot + postgres + redis),
  разворачивается на любой VPS/VM — обсуждался Yandex Cloud как вариант
- **Постинг в Instagram**: `instagrapi` напрямую (приватный API) — даёт
  `StoryLink`-стикер, которого нет в официальном Graph API. Библиотека
  синхронная, поэтому все вызовы уходят через `asyncio.to_thread`.
  HikerAPI — только на чтение, для постинга не годится (см. п.3)
- **Монтаж видео**: Vyra — интеграция через MCP, не обычный REST

## 5. CRM вместо дашборда

Кастомный веб-дашборд заменён на CRM-подход:
- **Notion** — стартовый вариант (быстро собрать, есть коннектор), но не
  полноценная CRM с автоматизацией — скорее гибкая БД с интерфейсом
- **Bitrix24** — вариант для масштабирования: Smart Process Automation под
  кастомные сущности «Аккаунт»/«Единица контента» с канбаном
- **Kommo** — промежуточный вариант между Notion и Bitrix24

Решение пока не принято окончательно; структура данных (`Account`/`ContentItem`
в `db/models.py`) спроектирована так, чтобы не зависеть от выбора CRM — она
общается с бэкендом через отдельный будущий API-слой, а не напрямую с ботом.

## 6. Промпты для AI-моделей

Отдельный слой, требующий внимания при реализации сервис-адаптеров:
- системный промпт оркестратора (Claude) уже есть в `services/claude_service.py`
- промпты под конкретные сценарии генерируются на лету из карточки аккаунта +
  собранных ответов
- промпты для Higgsfield/ElevenLabs/Vyra — у каждого сервиса свой синтаксис,
  подбираются эмпирически при реализации соответствующего адаптера
- предложение (не реализовано): хранить промпты не хардкодом в коде, а как
  версионируемые шаблоны (например, в CRM-таблице), чтобы редактировать без
  деплоя

## 7. Структура репозитория (`giga-bot/`)

```
config.py              # настройки + шаблон папок Drive + целевые количества контента
triggers.py             # словарь триггеров -> сценарий
fsm/states.py           # состояния диалогов
handlers/
  account.py             # /account N — переключение + привязка chat_id к аккаунту
  scenarios.py            # генерик-раннер диалогов, банк уточняющих вопросов,
                           # создание аккаунта (create_brand/create_blogger)
  approvals.py            # номер/эмодзи -> аппрув/отбраковка, PUBLISH_ROUTING,
                           # рабочий цикл перегенерации через revision_notes
  scheduler.py            # 12:00/15:00 напоминания, 20:00 публикация — привязано
                           # к реальным ChatBinding
services/
  claude_service.py       # оркестрация, генерация копирайта (+ revision_notes)
  drive_service.py         # создание папок, загрузка/листинг файлов
  vault.py                 # шифрование кредов (Fernet)
  instagram_service.py     # Instagram: рилс/фото/сторис через instagrapi (РЕАЛИЗОВАН)
  higgsfield_service.py    # фото/видео/лого (ЗАГЛУШКА — не блокирует MVP)
  elevenlabs_service.py    # озвучка (ЗАГЛУШКА — не блокирует MVP)
  vyra_service.py          # монтаж через MCP (ЗАГЛУШКА — Level 1)
  blotato_service.py       # TikTok — ВНЕ ОБЪЁМА, не подключён никуда
db/
  models.py                # Account, AccountPlatform (+external_account_id,
                            # is_connected), Credential, ContentItem,
                            # ChatBinding, GenerationJob, AuditLogEntry
  session.py                # async SQLAlchemy сессия
Dockerfile
docker-compose.yml       # bot + postgres + redis
requirements.txt
.env.example
bot.py                    # entrypoint
README.md
```

## 8. Что уже реализовано (не заглушка)

- Распознавание триггеров, генерик FSM-диалог с уточняющими вопросами
- `/account N` — переключение + запись `ChatBinding` в БД
- `create_brand`/`create_blogger` — реально создают `Account`, сеют
  `AccountPlatform(instagram)`, вызывают `drive_service.create_account_folder_tree`,
  привязывают чат
- Аппрув по номеру/списку/эмодзи, включая отбраковку пачки
- **Рабочий цикл перегенерации**: `GenerationJob` хранит scenario_id + answers +
  revision_notes; при ❌ вызывается `_generate_and_queue` заново с замечаниями,
  не просто эхо в чат
- `PUBLISH_ROUTING` — таблица решений «какой content_type → какой сервис
  публикации» (сама логика маршрутизации реальна, вызов адаптера — ещё TODO)
- Планировщик берёт реальные `(account_id, chat_id)` пары из БД, а не заглушку
- Redis для FSM в проде (`bot.py::_build_storage`, fallback на Memory для dev)
- Шифрование кредов, модель БД целиком
- Docker Compose топология (bot/postgres/redis)
